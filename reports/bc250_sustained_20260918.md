# BC-250 Bonsai sustained campaign (in progress)

Baseline source: `99596b3` (report-only child of `a687cc9`); optimization branch `experiment/bc250-sustained-20260918`. The preexisting working tree was clean. The untracked binary and shader blobs are preserved in `logs/bc250-sustained-20260918/baseline/` before edits; their hashes are recorded there.

## Decision protocol, set before candidates

- Primary workload: `q36-bench --vulkan -m gguf/Ternary-Bonsai-2-27B-Q2_0-g64.gguf --prompt-file tests/long_context_story_prompt.txt --ctx-start 512 --ctx-max 512 --ctx-alloc 641 --prefill-chunk 256 --gen-tokens 128`. The CSV must report exactly 512 prefill tokens and 128 greedy decode tokens. No MTP, batching, SSD streaming, or quality flags.
- Establish baseline spread with three uninstrumented, soak-gated runs at entry edge temperature at most 55 C. Candidate comparisons use at least three interleaved A/B pairs, alternating order, same binary flags and entry-temperature gate. Runs are independent; tokens within a run are not replicates.
- Report median and median absolute deviation for each arm and median paired percentage change. An end-to-end winner needs all pairs in the favorable direction, median gain greater than the larger of 1.5% and twice the baseline relative MAD, and no representative workload regression beyond the same uncertainty band. A marginal result gets seven pairs or is rejected as unproven. Profiled timings diagnose only; final verdict uses uninstrumented runs.
- Candidate correctness: compare complete fixed-prompt frontier logits and deterministic generated outputs against baseline, check longer repeated inference/reset, and use targeted packed-output parity for any preparation or quantization rewrite. Floating-point changes require an explicit tolerance before execution. Bit-exact claims require bit-exact outputs. Reject unexplained drift, bounds violations, or memory growth.
- No firmware, driver, voltage, or clock changes. Report telemetry sampled during measurements; do not treat the displayed DPM setting as sustained frequency.

## Experiment P1: Q2_0 MMQ token tile 128 -> 256

Fresh 40-CU profile (`runs/base-profile-65.txt`) attributes 2316 ms of the 512-token prefill to 800 Q2_0 MMQ dispatches; this is the largest prefill path. Each 128-token workgroup loads a 64-row Q2_0 weight tile and fills LDS for 128 token activations. The candidate uses eight wave32 subgroups for 256 tokens and one weight tile load, reducing duplicate weight tile loads and output-tile workgroups. It is selected only with `Q36_VK_Q2_MMQ_BN256=1` and `n_tok >= 192`; shorter tails retain the old shader. Weight and activation arithmetic, BK=32, and per-output reduction order are unchanged, so the expected output tolerance is **bit exact**. Larger LDS and 256-thread scheduling could lose occupancy; reject if the complete prefill path does not win. This is a tile experiment, not a sequence-chunk change.

Verdict: rejected. Frontier-512 complete logit JSON hashes match exactly. Three soak-gated interleaved pairs gave baseline pp512 197.38/198.82/196.33 t/s and candidate 188.09/190.36/190.74 t/s; median paired change -4.25%. Decode pair changes were -0.53%, +0.84%, -0.93%, with no meaningful gain. The implementation patch is preserved as `logs/bc250-sustained-20260918/p1-bn256-rejected.patch`; source reverted.

## Experiment D1: wave64 Hadamard max selection

The fresh decode profile attributes 100.46 ms / 64 generated tokens = 1.57 ms/token to `hadamard_prepare`. A 256-thread workgroup performs four independent 256-value Q8_K blocks, each represented by 64 threads after each thread's four-value local maximum. The production max selection uses six full workgroup barriers. On the selected wave64 size, a shuffle butterfly can choose the same `(absolute value, lowest index, signed value)` in each wave without those barriers. The remaining FWHT and block-sum barriers stay. The variant is selected by `Q36_VK_HADAMARD_SUBGROUP=1` only on a reported subgroup size of 64; the shader itself retains the original reduction when compiled at another subgroup size. Signed max value, fp64 scale arithmetic, byte packing, and output layout are unchanged. Expected tolerance is **bit exact** for finite inputs. A bounded packed-output harness will check zeros, signs, ties, small and large finite values, and supported widths/rows before full-model comparison. The upper bound is the 1.57 ms/token kernel, while shuffle and occupancy costs may erase the benefit.

Verdict: rejected as an end-to-end lever. `hadamard_parity.c` compared original and subgroup shaders on the GPU in 32 bounded fixtures; every packed byte matched. The selected shader was confirmed by the kernel profile (32 dispatches each; original 0.812 ms, subgroup 0.735 ms across tiny fixtures). In three primary-workload A/B pairs, baseline decode was 35.04/33.57/33.27 t/s and candidate 34.00/33.67/33.23 t/s; median paired change -0.12%. Prefill pair changes were +3.06%, -0.88%, -1.94%, also no reliable gain. Source was reverted; the patch and harness remain in the evidence directory. No claim is made for non-finite activation semantics, which the model does not support.

## Experiment P2: Q2_0 MMQ BK32 -> BK64

The Q2_0 MMQ prefill profile is 2316 ms / 512 real tokens. Each 256-element activation block currently executes eight BK32 slices with two shared-memory barriers per slice. The selectable `Q36_VK_Q2_MMQ_BK64=1` variant packs two adjacent slices into one LDS tile: four BK64 slices, eight fewer barrier pairs per block, unchanged BM64 and BN128, unchanged per-output FMA order. LDS rises from about 13 KiB to 25 KiB per workgroup; this may lower residency. The experiment tests whether barrier and reload cost outweigh that occupancy loss. Exact frontier logits are required before A/B; any unexplained bit drift rejects it. The source will be reverted unless pp512 improves beyond the predeclared gate without decode regression.

Verdict: rejected. The full frontier-512 logits JSON was byte identical. Three interleaved pairs yielded pp512 baseline 198.93/196.54/196.58 t/s and BK64 192.08/192.49/193.18 t/s; median paired change -2.06%, negative in all pairs. Decode differences were positive despite decode using the identical baseline shader and therefore do not identify a BK64 decode benefit. The patch is preserved as `logs/bc250-sustained-20260918/p2-bk64-rejected.patch`; source reverted.

## Experiment D2: attention split span 512 -> 256 at ctx512

The fresh decode profile attributes 91.39 ms / 65 tokens = 1.41 ms/token to `attn_decode_split`, plus 1.74 ms total for combine. The default 512-key span gives two split workgroups per head at the 512-token frontier. A 256-key span gives three, increasing available parallel work and shortening each scan while increasing partial writes and ordered combine work. This is selected with the existing `--attn-span 256`; no shader or model changes. Only an end-to-end win on batch-one decode can justify a shape-specific default. Different floating-point reduction order can change logits, so acceptance requires fixed generated-token behavior, maximum absolute final-logit error <= 1e-4 and no systematic drift across longer runs; these thresholds are set before testing. Prefill should be unchanged, aside from run noise.

Verdict: rejected on correctness. Three interleaved pairs gave decode baseline 33.66/32.73/32.85 t/s and span256 33.99/33.64/33.41 t/s (median paired +1.70%); prefill was mixed and its median paired change was -1.70%. A diagnostic build of the same source and shaders recorded all 128 greedy token IDs and logits at context 512 and 640. The token streams first differ at generated step 93. Frontier-512 logits are identical; final logits after the divergent sequences differ by up to 12.71, which is not a same-input numerical error estimate. Because generated behavior changed, the candidate fails the predeclared gate and no seven-pair extension was run. The diagnostic `q36_bench.c` change was reverted.

## Experiment P3: one real 512-token sequence chunk

The Bonsai GQA6 safety clamp currently limits graph prefill to 256 token rows, splitting pp512 into two batches even though the whole measured prefill takes about 2.6 seconds and the individual-dispatch watchdog is 10 seconds. A single 512-token chunk can reuse each weight load across more real tokens and may remove one round of graph preparation. This changes sequence chunking, not the MMQ BK/BN tile. Probe only context 512 with `Q36_VK_PREFILL_CHUNK_UNSAFE=1 --prefill-chunk 512`, while monitoring memory, GPU completion, and logits. Accept only if the 512-token prompt and 128-token decode remain correct, memory remains within budget, and interleaved uninstrumented pp512 wins without decode regression. Do not generalize the override to long contexts.

Verdict: rejected on correctness. The one-run pp512 result was 199.40 t/s at chunk256 versus 206.52 at chunk512, but the frontier-512 logit files differ at 248,320 entries: maximum absolute difference 0.3235, mean absolute difference 0.0383. The argmax happened to match; that does not repair the logit drift. Context-buffer estimate rose from 259.36 to 351.85 MiB. The observed drift is too large for a floating-point order tolerance and was not explained, so the predeclared correctness gate failed and no A/B speed extension was run. The diagnostic override is not retained.

## Experiment F1: fuse SwiGLU into Hadamard preparation

Source audit found a specific redundant result in the dense FFN: `swiglu_q8_k` writes both f32 `ffn_shared_mid` and unrotated Q8_K `inp_q8`, then the rotated down projection immediately runs `hadamard_prepare` on the f32 mid and consumes `had_q8`. For a rotated Q2_0 down weight, neither the unrotated Q8_K nor the intermediate f32 mid is needed by another consumer. The fusion boundary is gate/up f32 projections -> SwiGLU -> signs -> 1024-value FWHT -> four 256-value quant blocks -> down Q2_0. A single 256-thread workgroup owns each 1024-value transform block and its max/sum reductions; no workgroup barrier is used as a global synchronization mechanism. Each prepared Q8_K block is written once and shared by all down-projection output workgroups through the existing dispatch dependency. No activation preparation is duplicated across output tiles. The existing Hadamard shader uses about 8.25 KiB LDS per workgroup; the fused shader uses the same LDS and adds two input streams plus exponential arithmetic and live values during setup. Decode has only 17 workgroups for width 17408 on 40 CUs, so low occupancy is a serious risk; prefill has thousands of workgroups. The sign vector and Q2_0 down weights use the same prepared representation, and the path is restricted to that shape/type. Expected bit-exact packed Q8_K and logits for finite supported inputs; any mismatch rejects it. Selection is `Q36_VK_FUSE_SWIGLU_HAD=1`, with the existing two-dispatch path as fallback. The verdict is based on full prefill and decode, not dispatch count.

Verdict: rejected on end-to-end gain. A bounded GPU fixture compared 24 cases across widths 1024, 5120, 17408 and one/three rows, including zeros, signs, ties and deterministic random inputs; every packed Q8_K byte matched the two-stage path. Complete frontier-512 logits JSON was byte identical. Three interleaved pairs yielded decode baseline 33.83/33.24/33.11 t/s and fused 33.96/33.85/33.15 t/s; paired changes were +0.38%, +1.84%, +0.12% (median +0.38%, below the 1.5% gate). Prefill baseline 203.49/203.37/198.38 and fused 201.22/198.29/203.49 t/s was mixed. The patch and fixture are archived; source was reverted.

## Experiment D3: eight Q2_0 decode rows per workgroup

The Q2_0 decode shader loads a 256-entry LDS expansion table once per workgroup and computes four output rows. Doubling to eight rows halves workgroup count and amortizes table setup, but doubles live accumulators and weight work per group. A separate shader selected by `Q36_VK_Q2_DECODE_ROWS8=1` retains the production four-row fallback. Each output row retains its reduction order and packed arithmetic, so the required tolerance is bit exact. Complete decode throughput decides the experiment.

## Configuration and baseline evidence

`99596b3` is the baseline source revision and was HEAD when this campaign began. It is a report-only child of `a687cc9`; the sentence in `reports/decode_overhead_breakdown.md` saying `a687cc9` remained HEAD was stale. `6964c87` is an earlier MMQ merge, before the Q2_0 shared-LUT change `c910941`. The original untracked `q36-bench` and SPIR-V files were copied to `logs/bc250-sustained-20260918/baseline/`; `baseline/sha256.txt` identifies the blobs. Baseline executable SHA-256: `50f71990f4ffaef40e9bfcb842a32e93a2ecf39c8ee803bc7735253f558a7ff1`. Model SHA-256: `4f99aed01b8a877e153f9aa6569a4440fe17c59701cc0953e36d7f460549e70e`.

Live RADV query after the user's Vulkan fix reports AMD BC-250 / GFX1013, **40 active CUs**, maximum core DPM 2000 MHz, default subgroup 64 with subgroup-size control including 32. Q2 MMQ requests wave32; Q2 decode uses wave64. Kernel `7.2.6-1-cachyos`, Mesa RADV `26.2.2-arch3.2`, Vulkan instance 1.4.357 / device 1.4.354, glslc shaderc 2026.3 / glslang 16.4.0. Queue family 0 exposes one graphics+compute+transfer queue, family 1 sparse binding; the engine uses family 0 queue 0. The first pre-fix query reported 24 CUs and is not the benchmark configuration.

The model is a 7,626,008,928-byte GGUF v3 with 851 tensors: 402 Q2_0 (7,557,120,000 logical bytes), 96 BF16 (47,185,920 bytes), 353 F32 (10,582,016 bytes). Q2_0 comprises 6,717,440,000 code bytes and 839,680,000 scale bytes. This is GGUF header and shape accounting, not file-size-as-traffic. The model is mapped on the 15.35 GiB UMA device. At allocated context 641, runtime reports 259.36 MiB context buffers (93.46 scratch, 16.28 raw, 149.62 compressed) and 2060 KV bytes per token. The command takes exactly 512 real prompt tokens, then 128 greedy generated tokens with EOS skipping; MTP and batching are off.

Three uninstrumented baseline runs after entry edge temperature <=55 C yielded pp512 196.85, 199.06, 194.83 t/s (median **196.85**, MAD **2.02**) and decode 35.08, 34.87, 33.79 t/s (median **34.87**, MAD **0.21**). Active-load sampled median core clocks were 1970, 1930, 1760 MHz; edge temperatures reached 90, 91, 91 C and PPT medians were 142.4, 137.2, 124.0 W. The sysfs memory DPM display shows 450 MHz; no independent active memory-clock counter was available. These thermal/clock differences motivate paired comparisons.

Fresh profiled run at 40 CUs (`runs/base-profile-65.txt`) produced pp512 195.05 t/s and 65-token decode 31.74 t/s, roughly 0.9% and 9% below uninstrumented medians, though generation lengths differ and this is only a rough instrumentation comparison. Decode Q2 kernel sum is 1452.296/65 = **22.343 ms/token**; Hadamard 100.459/65 = 1.545, split attention 91.390/65 = 1.406, add/RMS normalization 66.315/65 = 1.020, recurrent delta-net 46.836/65 = 0.721. Decode GPU timestamp sum is 1853.710/65 = 28.519 ms/token. The profile reports 84,695 decode dispatches, 217.6 ms CPU record time, 130 flushes and 388.3 ms CPU wait time for 65 tokens. CPU waits include GPU completion and cannot be added to GPU time as independent overhead. Without a timestamped command-stream trace, summed GPU time and wall time do not establish full serialization or quantify inter-dispatch gaps.

Prefill at 512 real tokens has 2316.226 ms in Q2 MMQ across 800 dispatches, out of 2589.789 ms summed GPU time. Other profiled GPU components include Hadamard 71.136 ms, attention 44.065, delta-net 36.171, BF16 matmul 32.144, SwiGLU 19.883, recurrent convolution 18.229 and normalization 15.447. These sums do not independently measure barriers, bank conflicts or DRAM traffic. The Q2 MMQ uses FP16 pair FMAs, not an INT8 matrix instruction; nominal INT8 TOPS is not its ceiling.

## Traffic and timing reconciliation

The earlier 30.03 ms/token wall, 29.259 ms/token GPU sum, 22.961 ms/token dense and 6.298 ms/token remainder all belong to the `99596b3` report's **instrumented differential gen1 versus gen65** at context 512 (`logs/profiles/decode_diff_gen{1,65}.txt`). The 6.30 is GPU sum minus dense time, not an avoidable dispatch tax. Wall minus GPU is about 0.77 ms/token across measurement domains and cannot prove serialization or idle time. The fresh 40-CU profile above is a different run and must not be pooled with the earlier figures.

**3048 ms/128 = 23.813 ms/token** dense is the median of three cooler LUT-confirm runs (3038/3048/3111) in `karpathy/evidence/raw/r5-q2_0-lut.md`. **2937 ms/128 = 22.945 ms/token** is a separate mode-1 ablation in `logs/profiles/ablate-mode1-r1.txt`: weight loads remained but expansion and dot arithmetic were removed, producing invalid outputs. It is not a correctness-preserving memory floor. Mode 2 removed weight loads and took 589 ms/128. The 2937 figure is retracted as a floor because register allocation, occupancy, instruction mix and scheduling changed.

The historical **7.06 GB active stream** in `reports/optimization_results.md` was an estimate. The GGUF tensor ledger instead finds **7.1995392 GB** of Q2_0 tensors excluding token embedding, the logical once-per-token Q2 dense weight set: 6.3995904 GB code payload and 0.7999488 GB Q2 scales. The 7.626009 GB GGUF includes the 0.357581 GB token embedding, other tensors and header. The **8.44 GB container** in the request could not be traced to this model artifact. Neither container size is a traffic counter. BF16/F32 weights, activations, attention KV scans, recurrent state and temporary writes add accesses; cache hits, repeated fetches and transaction granularity change DRAM bytes. No hardware DRAM byte counter was available, so measured DRAM traffic is **unknown**. Dividing 7.1995392 GB by fresh dense kernel time 22.343 ms gives 322.2 GB/s of *logical weight bytes per kernel time*, not bus utilization.

Historical **385 GB/s** in `reports/optimization_results.md` divides estimated 7.06 GB by dense time after subtracting an output-invalid no-weight ablation; it is a modeled effective rate, not measured DRAM bandwidth. **357 GB/s** was an earlier effective/benchmark estimate and is not a transferable machine limit. **448 GB/s** and **454.4 GB/s** are nominal/spec-derived figures in older reports, without matching DRAM counters or active memory clocks in this campaign. A new standalone Vulkan test (`read_copy_bw.c`, 512 MiB working set exceeding 4 MiB L2, dependent checksum, seven GPU timestamp repeats) gives 236.5 GB/s useful contiguous shader reads, 219.9 GB/s useful strided reads and 369.5 GB/s for copy **reads plus writes**. The copy result is 184.75 GB/s per direction at that workload. These are logical useful bytes, not DRAM bytes; the lower synthetic read rate does not bound dense, whose access pattern/parallelism differs. No arbitrary efficiency factor is applied.

## Current causal limits

The graph requires a dispatch dependency where Q8 preparation feeds many output-row workgroups and where each layer's attention/recurrent state feeds the next. F1 fused one local producer/consumer boundary without an accepted gain. Hadamard workgroup barriers synchronize the 1024-value FWHT and quantization reductions; D1 removed only max-selection barriers with exact packed output but no full-model win. Q2 MMQ has two barriers per reduction slice; P2 doubled BK to halve their count, but larger LDS lost performance. Neither experiment isolates barrier cost because occupancy and scheduling changed. The 512-key attention scan is required work; D2's shorter split improved measured decode modestly but changed generated tokens. GDN token-to-token state order is required, while its prefill graph has batched matrix stages; treating all GDN prefill work as strictly serial would be false. Buffer-range hazard tracking and submit points in `q36_vulkan.c` remain broad in places, but no barrier removal was retained without race-free range analysis and command interval evidence. One exposed compute queue does not prove serial execution or exclude legal overlap. Counters for stalls, spills, LDS conflicts, bus bytes and per-dispatch intervals were unavailable, so neither bandwidth saturation nor bus idleness is established.

## D3 verdict and current stopping point

D3 is rejected on performance before additional correctness work. Three soak-gated interleaved pairs gave decode baseline 33.75/32.99/32.82 t/s versus rows8 31.42/31.40/31.25 t/s; paired changes were -6.90%, -4.82%, -4.78% (median -4.82%). Prefill moved +1.44%, +0.31%, +0.82% with the identical prefill shader, illustrating run noise rather than a decode-layout prefill benefit. The patch is `logs/bc250-sustained-20260918/d3-rows8-rejected.patch`; source and original binary/SPIR-V blobs were restored. No winning kernel change has been demonstrated in this campaign.

## Remaining work for continuation

The primary objective remains open. Source is back at `99596b3` on `experiment/bc250-sustained-20260918`; the campaign report and compact evidence should be committed, and no experimental shader should be merged merely because it passed parity. A successor should first collect an interval-level command trace or equivalent timestamped dispatch sequence to quantify dependency gaps and barrier scopes, rather than infer them from aggregate duration. The next decode experiment should target a measured recoverable component with a distinct hypothesis from the failed row-load pipeline, D1 subgroup max, D2 attention span, F1 fusion and D3 rows8. The next prefill experiment should inspect generated ISA/register/LDS allocation for the production MMQ and test a small, justified tile/scheduling change other than P1 BN256 or P2 BK64; P3 one-chunk512 failed logits correctness. Targeted GDN chunked prefill may be valuable only after deriving the exact state recurrence and checking intermediate state drift.

Secondary benchmarks remain to run: short prompt, longer prompt, longer filled-context decode, time to first token, peak GTT/RSS/VmSwap and repeated inference/reset memory growth. A same-length instrumented/uninstrumented comparison would isolate profiling overhead better than the current 65-versus-128 comparison. A hardware trace/counter capture would be needed to turn logical weight bytes into measured DRAM traffic and to separate latency, occupancy, spills and bandwidth. Current evidence establishes neither a decode bandwidth floor nor a prefill INT8 roofline. There is no final performance gain to claim; the final active implementation is the baseline.
