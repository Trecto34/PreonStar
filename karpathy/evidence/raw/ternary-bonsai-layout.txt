## Phase (b): CONFIRMED against the publisher reference implementation
The 34-byte structure above was derived purely from offsets. The fork's own
source matches it byte for byte (ggml/src/ggml-common.h):

    #define QK_PQ2_0 128
    typedef struct {
        ggml_half d;
        uint8_t   qs[QK_PQ2_0/4];
    } block_pq2_0;                              /* 2 + 32 = 34 bytes */

and its enum (ggml/include/ggml.h):

    GGML_TYPE_Q2_0   = 42,
    GGML_TYPE_PQ2_0  = 142,   // Prism-private ternary, group 128
    GGML_TYPE_PTQ1_0 = 143,   // Prism-private ternary, group 128
    GGML_TYPE_COUNT  = 144,

The fork comment states PQ2_0 is the same 2-bit codec as upstream Q2_0
(group 64) but with ONE fp16 scale per 128 weights instead of per 64
(~5% smaller), and carries a distinct type id so it coexists with upstream's
group-64 Q2_0 (type 42).

## Codebook: RESOLVED (no longer an open question)
Read from the reference implementation, ggml/src/ggml-quants.c,
dequantize_row_pq2_0():

    const uint8_t q = (x[i].qs[byte_index] >> bit_offset) & 0x03;
    // 00=-1, 01=0, 10=+1, 11=+2
    y[i*qk + j] = ((int)q - 1) * d;

CORRECTION to the earlier revision of this file, which guessed there was one
unused fourth code. There is not. All four codes are live: -1, 0, +1, +2 over
a single fp16 scale per 128 weights. Two consequences:
  - the format is 4-level, not ternary; the third magnitude level (+2) buys
    the extra precision that lets 2.125 bpw land close to the 27B's quality;
  - the multiply-free property SURVIVES: y += d*(sum_{10} x - sum_{00} x
    + 2*sum_{11} x) is still masks, adds and one shift. No per-weight multiply.

## Why the BC-250 specifically cannot run it fast yet: no Vulkan kernels
The fork implements PQ2_0 on CPU, CUDA and Metal - NOT Vulkan. Checked
directly: `grep -rn 'PQ2_0' ggml/src/ggml-vulkan.cpp` returns nothing, and
the fork's Vulkan shader directory carries no q2_0/pq2_0/ternary shader.
This box is RADV GFX1013, so the fork can only run this model on the CPU
(dense CPU kernels: ggml_vec_dot_pq2_0_q8_0, ggml_gemv_pq2_0_4x8_q8_0,
ggml_gemm_pq2_0_4x8_q8_0 - real tuned 4x8 kernels, not a naive fallback).

Therefore the "run it fast" path stays what CAMPAIGN.md section 6 item 6
records: port type 142 to q36's Vulkan backend. The port is now fully
specified - block struct, group size, scale placement and the four code
values are all known from the reference, so it is a transcription job
(types entry + row dequant + one GEMV), not format research.

## Still not implemented anywhere locally: the Hadamard rotation
prism.hadamard.weight_names / inverse_weight_names apply an FWHT to
token_embd and the quantised weights. The fork carries this in the graph
side (grep 'hadamard' hits src/llama-model.cpp, src/llama-graph.cpp,
ggml/src/ggml-cuda/ggml-cuda.cu) - but notably NOT in its model loader.
q36 has no inverse-Hadamard at all. Weights must not be dequantised without
it or the output is numerically meaningless even though it "runs".
